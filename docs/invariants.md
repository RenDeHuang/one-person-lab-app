# One Person Lab App Invariants

Owner: `one-person-lab-app`
Purpose: `app_invariants`
State: `active_truth`
Machine boundary: Human-readable invariants. Machine-readable truth lives in `contracts/`, source, release artifacts, updater metadata, and test results.

- The App repo owns desktop product packaging, release metadata, first-run product policy, App-level contracts, screenshots, user guides, and App validation wrappers.
- Temporary visual, Playwright, and Codex screenshots are local run artifacts, not repo truth. Keep them out of git unless they are promoted into `docs/site/latest`, a release evidence bundle, or an explicit manifest-backed evidence surface.
- The App repo is a purpose-first Codex wrapper product authority. It owns how users enter research, grant, presentation, and book work; it does not own the runtime, domain, memory, artifact, or family production truth behind those entries.
- The App repo owns One Person Lab App GUI product truth. The active shell may implement renderer/process/package/test/release-hook details and absorb upstream AionUI changes, but App page behavior, model-selection policy, onboarding policy, screenshots, and release/user docs stay App-owned.
- GUI 定义必须按
  `gui_definition_stack: product_definition > visual_system > shell_implementation_conformance`
  从 App-owned product docs 流向 implementation。Product definition 入口是
  `docs/product/gui/README.md`、
  `docs/product/gui/ideal-interaction-spec.md`、
  `docs/product/gui/codex-to-opl-app-delta.md`、
  `docs/product/gui/feature-inventory.md` 和 App contracts；visual system 与
  shell implementation/conformance 入口统一由
  `docs/product/gui/README.md` 路由。
- Shell authority is `gui_shell_authority: implementation_only`. Shell code,
  screenshots, upstream defaults, visual QA, and local implementation state may
  prove implementation or record a deviation, but cannot redefine App product
  truth or override a higher GUI definition layer.
- The current GUI visual/interaction reference is ChatGPT Codex macOS
  `26.707.41301` observed on `2026-07-11`. The ideal/native target requires the
  desktop workspace/session rail visible and inspector closed by default. The
  active AionUI state is read dynamically from
  `contracts/app-product-profile.json#gui.home.home_layout` and compared with
  that ideal; governance must report current conformance or deviation without
  freezing the current active values.
- The App ordinary path is a Codex CLI fixed-executor experience with configurable professional-agent shortcuts. First-party starter registry entries and starter shortcuts are defaults, not the upper bound of what OPL App can manage. It must not expose Aion CLI, Claude Code, or generic backend/provider switching as normal user choices; App-owned model/reasoning and user-language permission/access controls remain visible at the composer decision point.
- The OPL Agent Registry is a configurable GitHub/URL discovery directory only. Each selected agent manifest URL becomes install authority only after OPL Framework validation, package lock, rollback ref, and receipt creation. The current App contract/readback slice covers registry refresh, manifest validation, starter manifest schema/fixtures, selected install lock/receipt, install/update/repair/uninstall action receipts, package exposure preference receipts for hide/unhide/enable/disable, Home shortcut preference receipt/readback, list/status readback, active-shell launch-only invocation receipts, active-shell Settings `physical_surface` display, and Framework-owned manifest-declared local Codex plugin materialization into `CODEX_HOME` plugin cache, OPL state marketplace wrappers, Codex config tables, package lock `physical_surface`, action receipt `physical_surface`, and required skill payload ids/paths readback; non-live first-party distribution payload proof and remote payload manifest fields are contract/Framework-owned; installed Codex-surface reload proof and live user-path evidence still require separate runtime or release-owner evidence. Settings Capabilities must treat installed packages as the primary identity, with Home shortcut controls inline and purpose only as a tag/filter. Canonical runtime projection is `app_state.agent_packages.directory + app_state.agent_packages.status_index`; the shell may normalize from `app_state.modules.items[]` only as rollout fallback, but it must preserve multi-axis source/update/trust/Codex-surface semantics and must not collapse developer checkouts into a generic repair state. Agent Package `rollback_ref` is a displayed recovery reference, not an App- or Framework-owned package lifecycle rollback verb; Managed Update/runtime substrate/package-channel owners keep true managed rollback authority. The Registry must not define agent business behavior, and the App must stay limited to discovery, selection, management UI, launch receipt display, and refs-only status.
- The App home professional-agent shortcuts are not backend selectors and not strong session contracts. They launch Codex with the selected package's declared plugin/skill surface, and each created conversation must carry an App-owned invocation receipt that records launch facts only. The App must not use shortcut/profile metadata to decide domain workflow, prompt internals, stage behavior, artifact schema, readiness verdict, quality/export authority, or owner receipts.
- Ordinary Settings navigation 由 App 拥有。Settings is the App OPL Control Center and must organize ordinary pages by user questions: Overview, Access, Workspace, Agents & Capabilities, Resources & Connections, Maintenance, Data & Storage, and Preferences. Advanced, About, Update, Theme, and Local Services are secondary/deep-link surfaces. User-needed capabilities must appear as task entries, not AionUI technical tabs: Model & Account, Workspace, Maintenance Hub, Capability Status, Web / Remote Access, Resources & Connections, Developer Profile Status, External Tools & Voice, and Custom Assistant. Agents & Capabilities is an installed package directory with integrated Home shortcut management, multi-axis package status, and detail disclosure; purpose is secondary metadata, not the primary identity. Access first screen owns OPL Gateway, Codex CLI, and local browser access only; Resources & Connections owns Docker WebUI, OPL Workspace, managed resources, SSH/HPC, Fabric, and Console-managed refs. About is version/link/feedback/readback information; Update is explicit update detail; Maintenance owns normal update and repair actions and must not host in-progress task progress. Data & Storage owns receipt-backed cleanup controls. `contracts/app-settings-control-plane.json` is the machine-readable Settings registry and route behavior boundary over `settings_ia.v1`: current route ids stay distinct from user-facing groups, ordinary route ids stay `general` / `access` / `workspace` / `capabilities` / `resources` / `environment` / `storage` / `appearance`; `SettingsHost` and `SettingsShellAdapterSlot` are shell adapter slots, not shell-owned product IA; Access, Maintenance/Environment, Data & Storage, and Agents & Capabilities consume explicit view-model adapter entries; Settings search only filters route labels, task entries, and action keywords; visual QA evidence covers all eight ordinary routes across desktop/mobile viewports with a manifest and explicit secondary-route evidence; and Advanced/About/Update/Theme/Local Services stay secondary or deep-link routes unless the contract, page-state matrix, validators, tests, and visual QA targets are updated together. Legacy overview/runtime/system/model/agent/assistants/skills-hub/tools/display/webui/pet routes 必须 redirect 到 App-owned pages，不能成为 normal user paths。
- `contracts/app-settings-control-plane.json#product_system_checklist` is the Settings Control Center completion-audit source. Each item requires fresh evidence for the slice being claimed. Installed App currentness, notarization, running version, and release readiness remain explicit release-owner-gated items and must not be inferred from Settings contracts, shell tests, screenshot QA, pushed commits, or active-shell validation.
- Settings visual QA is active-shell behavior evidence only. Screenshot or E2E visual coverage for Settings routes can close UI structure and overlap/framing risks, but it must not be used as release readiness, packaged App readiness, runtime currentness, owner acceptance, or production readiness evidence.
- AionUI Settings upstream intake must be classified as `accepted`, `adapt`, `redirect`, or `reject` before entering the Settings registry, `SettingsHost`, or `SettingsShellAdapterSlot`. Accepted/adapted entries need registry or slot evidence; redirected/rejected entries must go through legacy redirect, extension anchor remap, or forbidden probes. This classification does not prove release readiness.
- AionUI Settings fork maintenance uses the existing App-owned Settings Control Plane plus thin shell adapter. Do not introduce a parallel Settings package, plugin ecosystem, overlay topology, or shell-owned product IA unless the App contracts first define a concrete gap that the existing registry, adapter slot, view-model adapters, and upstream intake gate cannot cover.
- GUI behavior changes must land first in App-owned contracts, docs, page-state tests, and release gates. Shell implementation follows those App-owned boundaries.
- App install/exposure policy keeps `skill` as the public semantic ABI. Codex App plugins may package MAS/MAG/RCA/BookForge/OMA and third-party professional-agent skills, but plugin packaging must not create second semantics or duplicate bare `~/.codex/skills/{med-autoscience,med-autogrant,redcube-ai,opl-bookforge}` mirrors.
- App capability presentation must preserve the OPL three-layer semantics: professional Skill is the expert playbook, skill-local deterministic helper is packaged support material such as `kernel.py`, and programmatic substrate / authority surface is Framework or domain-owned runtime, connector, receipt, owner-gate, App-state, or release evidence. The App may display all three as package/readback facts, but must not collapse them into one "skill installed means ready" state.
- Workflow dependencies are separate from family domain plugin surfaces. The App stores only its domain/additional package entries; OfficeCLI, MinerU, UI/UX, conflict retirement, and model recommendation come from OPL Flow policy and are executed by Framework. Full may project that closure into the active shell for compatibility but must not own a second list.
- The App repo owns the GUI runtime bridge contract; OPL owns the runtime/app CLI protocol; the active shell only implements the replaceable adapter.
- `opl app state --profile fast --json` is the default GUI state and refresh source; `opl app state --profile full --json` is explicit full-state diagnostic or release-evidence state; `opl app action execute --action <id> [--payload <json>] [--dry-run] --json` is the App mutation boundary.
- `opl runtime app-operator-drilldown --detail full --json` is only the runtime/Operator full drilldown exception.
- Runtime page default attention is running activity first, then active project lines, project progress, and next visible owner action. Full evidence ledger content must stay secondary, on-demand, diagnostic, or release-evidence scoped.
- OPL App and OPL Workspace are equivalent App surfaces: desktop App, Docker/WebUI, and Workspace consume the same App contracts and Framework state/action boundary. Workspace hosting details such as URL, account, isolation, storage volume, and managed-resource receipts must not become a second App product truth.
- OPL Fabric appears in the App as refs-only resource context: OPL Gateway for AI access, OPL Connect for connector readiness, compute/storage refs for execution, Environment Catalog refs for template/version/source/task fit, and resource receipts for plan/approve/execute/monitor/collect flows. The App must not own Fabric compute scheduling, storage authority, connector credentials, environment bodies, billing, or Console policy truth.
- OPL Console is the management surface for organization policy, quota, billing, permissions, Workspace lifecycle, connector approval, environment policy, and managed resource packages. Console-managed resources display policy/quota/billing/permission refs; user-provided local, SSH, or HPC resources remain self-managed in App display unless the Framework projection marks them as Console-managed.
- The App must not own OPL runtime truth, provider implementation, domain truth, domain quality verdicts, memory body, artifact body, artifact authority, or owner receipt authority.
- External learning landings, including K-Dense BYOK learning, OpenClaudeScience / Claude Science workbench framing, and AGUI proof lessons, must not create a second runtime, domain, provider, billing, artifact, owner-receipt, or release-readiness truth. Reusable lessons must land as App contracts/profile/docs/tests, candidate adapter requirements, or Framework producer-ref requests.

Standard updater assets update only the macOS App carrier variant (`One Person Lab.app` and updater metadata), not OPL Runtime Fabric, Capability Packages, Companion Tools, Codex Surface, Workflow Profile, User Data/Artifacts, WebUI images, Linux package carriers, Homebrew/system tools, or developer checkout sources.

Legacy machine ids such as `runtime_substrate`, `runtime_toolchain`, `agent_package_channel`, and `capability_exposure` may appear only as internal contract/readback ids, not as primary user terms.

It must not upgrade, rewrite, or silently override a user's global Codex, Homebrew Codex, or system Codex install. OPL Runtime Fabric defaults to App-owned runtime; compatible system PATH, Homebrew, global tools, and developer checkouts may be detected for diagnostics, but require explicit expert opt-in to use and remain unmanaged.

MAS/MAG/RCA/OMA/BookForge are `domain_agent_package`, MAS Scholar Skills is a `framework_capability_package`, and OPL Flow is a `workflow_plugin_package`; all use the same package lifecycle and only differ by package kind. GHCR `latest` is the ordinary user package channel when a package is release-published; immutable version tags plus resolved digests are the installed truth. Clean managed roots may be silently updated in background maintenance, and each update must refresh the Codex Surface when needed. Dirty checkouts, developer checkouts, idempotency locks, verification failures, permission changes, and manual-required conditions must not be overwritten.
- OPL Flow is a required Standard and Full workflow plugin package, not a standard updater or WebUI image target. App/CLI setup installs or refreshes it with `python3 scripts/install_local_plugin.py`. Workflow Profile sync installs missing profile files or emits a semantic merge packet and must not silently overwrite existing user `AGENTS.md` or `TASTE.md`.
- GitHub repo or local checkout module sources are an explicit Developer Profile `source_channel` opt-in, not a normal-user default. Settings must express Developer Profile capabilities across `source_channel`, `workspace_trust`, `github_authority`, `agent_automation`, and `runtime_mutation_scope`, rather than a single Developer Mode switch.
- App release/user-path evidence is cohort-bound App evidence. It must not be used as stable/latest promotion, MAS/MAG/RCA/BookForge domain readiness, or OPL family production readiness without the separate owner decisions and evidence gates.

App-owned contracts, active-shell adapter sync, AionUI mainline behavior, `opl-native-workbench` foreground-alternative boundaries, page-state matrices, route receipts, first-run policy, Settings / Storage, release-boundary validators, runtime/domain no-authority guards, and AGUI archived-proof boundary cleanup are functional/structural lanes and may close before release cohorts, clean-VM proof, packaged `.app` smoke, same-cohort user-path artifacts, real user-directory E2E, owner acceptance, or production-ready claims. Those later items remain mandatory release/lifecycle evidence lanes; shell tests, App validation, contract validation, UI rendering, or docs updates cannot replace them.

- App page-state behavior must consume framework-owned read models and refs-only action routes; it must not infer domain ready, production ready, quality verdict, release ready, or artifact authority from provider completion or UI rendering alone.
- App docs are human-readable navigation and product guidance. Machine decisions must use contracts, source, release artifacts, updater metadata, and test outputs.

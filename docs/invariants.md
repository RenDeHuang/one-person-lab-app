# One Person Lab App Invariants

Owner: `one-person-lab-app`
Purpose: `app_invariants`
State: `active_truth`
Machine boundary: Human-readable invariants. Machine-readable truth lives in `contracts/`, source, release artifacts, updater metadata, and test results.

- The App repo owns desktop product packaging, release metadata, first-run product policy, App-level contracts, screenshots, user guides, and App validation wrappers.
- The App repo is a purpose-first Codex wrapper product authority. It owns how users enter research, grant, presentation, and book work; it does not own the runtime, domain, memory, artifact, or family production truth behind those entries.
- The App repo owns One Person Lab App GUI product truth. The active shell may implement renderer/process/package/test/release-hook details and absorb upstream AionUI changes, but App page behavior, model-selection policy, onboarding policy, screenshots, and release/user docs stay App-owned.
- GUI 定义必须从 App-owned product docs 流向 implementation：
  `docs/product/gui/ideal-interaction-spec.md` 定义交互模型，
  `docs/product/gui/codex-to-opl-app-delta.md` 定义 OPL 产品增量，
  `docs/product/gui/feature-inventory.md` 维护跨 shell 能力清单。
- The App ordinary path is a Codex CLI fixed-executor experience with configurable professional-agent shortcuts. First-party starter registry entries and starter shortcuts are defaults, not the upper bound of what OPL App can manage. It must not expose Aion CLI, Claude Code, generic backend/provider switching, or permission-mode selectors as normal user choices; model control stays in the App-owned Codex model selector/status.
- The OPL Agent Registry is a configurable GitHub/URL discovery directory only. Each selected agent manifest URL becomes install authority only after OPL Framework validation, package lock, rollback ref, and receipt creation. The current App contract/readback slice covers registry refresh, manifest validation, starter manifest schema/fixtures, selected install lock/receipt, update/repair/rollback/uninstall/hide/unhide/enable/disable/status lifecycle receipts, Home shortcut preference receipt/readback, list readback, active-shell launch-only invocation receipts, active-shell Settings `physical_surface` display, and Framework-owned manifest-declared local Codex plugin materialization into `CODEX_HOME` plugin cache, OPL state marketplace wrappers, Codex config tables, package lock `physical_surface`, lifecycle receipt `physical_surface`, and required skill payload ids/paths readback; non-live first-party distribution payload proof and remote payload manifest fields are contract/Framework-owned; installed Codex-surface reload proof and live user-path evidence still require separate runtime or release-owner evidence. Settings Capabilities must treat installed packages as the primary identity, with Home shortcut controls inline and purpose only as a tag/filter. Canonical runtime projection is `app_state.agent_packages.directory + app_state.agent_packages.status_index`; the shell may normalize from `app_state.modules.items[]` only as rollout fallback, but it must preserve multi-axis source/update/trust/Codex-surface semantics and must not collapse developer checkouts into a generic repair state. The Registry must not define agent business behavior, and the App must stay limited to discovery, selection, management UI, launch receipt display, and refs-only status.
- The App home professional-agent shortcuts are not backend selectors and not strong session contracts. They launch Codex with the selected package's declared plugin/skill surface, and each created conversation must carry an App-owned invocation receipt that records launch facts only. The App must not use shortcut/profile metadata to decide domain workflow, prompt internals, stage behavior, artifact schema, readiness verdict, quality/export authority, or owner receipts.
- Ordinary Settings navigation 由 App 拥有。Settings is the App OPL Control Center and must organize ordinary pages by user questions: Overview, Access, Workspace, Capabilities, Resources & Connections, Maintenance & Updates, Data & Storage, and Preferences. Advanced, About, Update, Theme, and Local Services are secondary/deep-link surfaces. User-needed capabilities must appear as task entries, not AionUI technical tabs: Model & Account, Workspace, Maintenance Hub, Capability Status, Web / Remote Access, Resources & Connections, Developer Profile Status, External Tools & Voice, and Custom Assistant. Capabilities is an installed package directory with integrated Home shortcut management, multi-axis package status, and detail disclosure; purpose is secondary metadata, not the primary identity. Access first screen owns OPL Gateway, Codex CLI, and local browser access only; Resources & Connections owns Docker WebUI, OPL Workspace, managed resources, SSH/HPC, Fabric, and Console-managed refs. About is version/link/feedback/readback information; Update is explicit update detail; Maintenance & Updates owns normal update and repair actions and must not host in-progress task progress. Data & Storage owns receipt-backed cleanup controls. `contracts/app-settings-control-plane.json` is the machine-readable Settings registry and route behavior boundary over `settings_ia.v1`: current route ids stay distinct from user-facing groups, ordinary route ids stay `general` / `access` / `workspace` / `capabilities` / `resources` / `environment` / `storage` / `appearance`; `SettingsHost` and `SettingsShellAdapterSlot` are shell adapter slots, not shell-owned product IA; Access, Environment, Storage, and Capabilities consume explicit view-model adapter entries; Settings search only filters route labels, task entries, and action keywords; visual QA evidence covers all eight ordinary routes across desktop/mobile viewports with a manifest and explicit secondary-route evidence; and Advanced/About/Update/Theme/Local Services stay secondary or deep-link routes unless the contract, page-state matrix, validators, tests, and visual QA targets are updated together. Legacy overview/runtime/system/model/agent/assistants/skills-hub/tools/display/webui/pet routes 必须 redirect 到 App-owned pages，不能成为 normal user paths。
- `contracts/app-settings-control-plane.json#product_system_checklist` is the Settings Control Center completion-audit source. Each item requires fresh evidence for the slice being claimed. Installed App currentness, notarization, running version, and release readiness remain explicit release-owner-gated items and must not be inferred from Settings contracts, shell tests, screenshot QA, pushed commits, or active-shell validation.
- Settings visual QA is active-shell behavior evidence only. Screenshot or E2E visual coverage for Settings routes can close UI structure and overlap/framing risks, but it must not be used as release readiness, packaged App readiness, runtime currentness, owner acceptance, or production readiness evidence.
- AionUI Settings upstream intake must be classified as `accepted`, `adapt`, `redirect`, or `reject` before entering the Settings registry, `SettingsHost`, or `SettingsShellAdapterSlot`. Accepted/adapted entries need registry or slot evidence; redirected/rejected entries must go through legacy redirect, extension anchor remap, or forbidden probes. This classification does not prove release readiness.
- AionUI Settings fork maintenance uses the existing App-owned Settings Control Plane plus thin shell adapter. Do not introduce a parallel Settings package, plugin ecosystem, overlay topology, or shell-owned product IA unless the App contracts first define a concrete gap that the existing registry, adapter slot, view-model adapters, and upstream intake gate cannot cover.
- GUI behavior changes must land first in App-owned contracts, docs, page-state tests, and release gates. Shell implementation follows those App-owned boundaries.
- App install/exposure policy keeps `skill` as the public semantic ABI. Codex App plugins may package MAS/MAG/RCA/BookForge/OMA and third-party professional-agent skills, but plugin packaging must not create second semantics or duplicate bare `~/.codex/skills/{med-autoscience,med-autogrant,redcube-ai,opl-bookforge}` mirrors.
- Companion skill sync is separate from family domain plugin surfaces. `default_packaged_codex_skill_ids` is the App-level whitelist for default packaged and default visible skills during the current migration, regardless of whether a candidate comes from AionUI builtin assets, Skills Manager, Codex local skills, or plugin payloads. Shared skills such as Superpowers, cron, the OfficeCLI family, PDF, MinerU, and UI/UX helpers may sync to user skill discovery paths; first-party professional agents stay plugin-visible package routes unless their package manifest explicitly declares a shared skill pack. Required external skill packs such as MAS professional skills may be developed in separate repos, but ordinary release/install must materialize them into the owning Agent Package with lock/checksum/receipt evidence.
- The App repo owns the GUI runtime bridge contract; OPL owns the runtime/app CLI protocol; the active shell only implements the replaceable adapter.
- `opl app state --profile fast --json` is the default GUI state and refresh source; `opl app state --profile full --json` is explicit full-state diagnostic or release-evidence state; `opl app action execute --action <id> [--payload <json>] [--dry-run] --json` is the App mutation boundary.
- `opl runtime app-operator-drilldown --detail full --json` is only the runtime/Operator full drilldown exception.
- Runtime page default attention is running activity first, then active project lines, project progress, and next visible owner action. Full evidence ledger content must stay secondary, on-demand, diagnostic, or release-evidence scoped.
- OPL App and OPL Workspace are equivalent App surfaces: desktop App, Docker/WebUI, and Workspace consume the same App contracts and Framework state/action boundary. Workspace hosting details such as URL, account, isolation, storage volume, and managed-resource receipts must not become a second App product truth.
- OPL Fabric appears in the App as refs-only resource context: OPL Gateway for AI access, OPL Connect for connector readiness, compute/storage refs for execution, Environment Catalog refs for template/version/source/task fit, and resource receipts for plan/approve/execute/monitor/collect flows. The App must not own Fabric compute scheduling, storage authority, connector credentials, environment bodies, billing, or Console policy truth.
- OPL Console is the management surface for organization policy, quota, billing, permissions, Workspace lifecycle, connector approval, environment policy, and managed resource packages. Console-managed resources display policy/quota/billing/permission refs; user-provided local, SSH, or HPC resources remain self-managed in App display unless the Framework projection marks them as Console-managed.
- The App must not own OPL runtime truth, provider implementation, domain truth, domain quality verdicts, memory body, artifact body, artifact authority, or owner receipt authority.
- External learning landings, including K-Dense BYOK learning, OpenClaudeScience / Claude Science workbench framing, and AGUI proof lessons, must not create a second runtime, domain, provider, billing, artifact, owner-receipt, or release-readiness truth. Reusable lessons must land as App contracts/profile/docs/tests, candidate adapter requirements, or Framework producer-ref requests.
- `shells/aionui/` remains an external checkout of `gaofeng21cn/opl-aion-shell`; this repo must not merge or vendor AionUI history into the App default branch.
- Future GUI shell candidates are declared in `contracts/app-shell-candidates.json`; selectable candidates also get their own repo-relative adapter contract under `contracts/shell-adapters/`. `opl-native-workbench` is the foreground alternative candidate when the registry selects it, with an independent external checkout at `shells/opl-native-workbench`; Hermes is retained as the prior foreground alternative reference; AGUI remains archived technical proof. The default release shell remains `contracts/app-shell-adapter.json`; explicit candidate builds must set `OPL_APP_SHELL_ADAPTER_CONTRACT`, compile a launchable `.app` bundle manifest, and must not change stable/nightly release gates or updater metadata. A candidate becomes the default release shell only after `contracts/app-shell-adapter.json` is changed deliberately and the App shell adapter, product profile sync, page-state/first-run matrices, active-shell validation, GUI package compile, and external checkout history policy all pass.
- Standard updater assets and Full first-install assets stay separate. Updater metadata must not select assets whose names include `Full`.
- Full first-install assets preload payloads for clean machines; they are not a long-term update channel. Standard updater assets update only the macOS App carrier variant (`One Person Lab.app` and updater metadata), not OPL Runtime Fabric, Capability Packages, Companion Tools, Codex Surface, Workflow Profile, User Data/Artifacts, WebUI images, Linux package carriers, Homebrew/system tools, or developer checkout sources.
- App install/update documentation and Settings copy use seven user-facing layers: Installation Carrier, OPL Runtime Fabric, Capability Packages, Companion Tools, Codex Surface, Workflow Profile, and User Data/Artifacts. Legacy machine ids such as `runtime_substrate`, `runtime_toolchain`, `agent_package_channel`, and `capability_exposure` may appear only as internal contract/readback ids, not as primary user terms.
- `embedded_codex_executor` is the App-owned Codex CLI executor payload in OPL Runtime Fabric. It must not upgrade, rewrite, or silently override a user's global Codex, Homebrew Codex, or system Codex install. OPL Runtime Fabric defaults to App-owned runtime; compatible system PATH, Homebrew, global tools, and developer checkouts may be detected for diagnostics, but require explicit expert opt-in to use and remain unmanaged.
- OPL Packages are the ordinary non-development Capability Packages distribution source for MAS/MAG/RCA/BookForge/OMA/ScholarSkills. GHCR `latest` is the only ordinary user package channel; daily automation may move it only after package gates pass, while immutable version tags plus resolved digests are the installed truth. Clean managed roots may be silently updated in background maintenance, and each update must refresh the Codex Surface when needed. Dirty checkouts, developer checkouts, idempotency locks, verification failures, permission changes, and manual-required conditions must not be overwritten.
- OPL Flow is a Workflow Profile surface, not a standard updater, WebUI image, or module package target. Workflow Profile sync must not silently overwrite existing user `AGENTS.md` or `TASTE.md`; existing profiles require a Codex semantic merge packet.
- GitHub repo or local checkout module sources are an explicit Developer Profile `source_channel` opt-in, not a normal-user default. Settings must express Developer Profile capabilities across `source_channel`, `workspace_trust`, `github_authority`, `agent_automation`, and `runtime_mutation_scope`, rather than a single Developer Mode switch.
- App release/user-path evidence is cohort-bound App evidence. It must not be used as stable/latest promotion, MAS/MAG/RCA/BookForge domain readiness, or OPL family production readiness without the separate owner decisions and evidence gates.
- Live Evidence deferred / functional structure first is the App development rule. App-owned contracts, active-shell adapter sync, AionUI mainline behavior, `opl-native-workbench` foreground-alternative boundaries, page-state matrices, route receipts, first-run policy, Settings / Storage, release-boundary validators, runtime/domain no-authority guards, and AGUI archived-proof boundary cleanup are functional/structural lanes and may close before release cohorts, clean-VM proof, packaged `.app` smoke, same-cohort user-path artifacts, real user-directory E2E, owner acceptance, or production-ready claims. Those later items remain mandatory release/lifecycle evidence lanes; shell tests, App validation, contract validation, UI rendering, or docs updates cannot replace them.
- First-run Core ready can use bundled runtime payloads; repo sync, module reconcile, CLT installation, companion skills, and ecosystem module updates remain background maintenance after Core ready.
- App page-state behavior must consume framework-owned read models and refs-only action routes; it must not infer domain ready, production ready, quality verdict, release ready, or artifact authority from provider completion or UI rendering alone.
- App docs are human-readable navigation and product guidance. Machine decisions must use contracts, source, release artifacts, updater metadata, and test outputs.

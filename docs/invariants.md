# One Person Lab App Invariants

Owner: `one-person-lab-app`
Purpose: `app_invariants`
State: `active_truth`
Machine boundary: Human-readable invariants. Machine-readable truth lives in `contracts/`, source, release artifacts, updater metadata, and test results.

- The App repo owns desktop product packaging, release metadata, first-run product policy, App-level contracts, screenshots, user guides, and App validation wrappers.
- Temporary visual, Playwright, and Codex screenshots are local run artifacts, not repo truth. Keep them out of git unless they are promoted into `docs/site/latest`, a release evidence bundle, or an explicit manifest-backed evidence surface.
- The App repo is a purpose-first Codex wrapper product authority. It owns how users enter research, grant, presentation, and book work; it does not own the runtime, domain, memory, artifact, or family production truth behind those entries.
- The App repo owns One Person Lab App GUI product truth. The active shell may implement renderer/process/package/test/release-hook details and absorb upstream AionUI changes, but App page behavior, model-selection policy, onboarding policy, screenshots, and release/user docs stay App-owned.
- Conversation/session backed by the canonical Codex App Server thread ID is the primary user-work unit. Project affinity is `unbound | bound` and has zero-or-one cardinality: a new session may start projectless or bound. Only `custom_workspace=false` or no canonical recorded cwd may enter user-triggered one-time adoption; it writes `thread/settings/update.cwd`, requires exact `thread/read`, and commits local projection only after the returned cwd matches. Existing recorded cwd blocks `bound(A) -> bound(B)` reassignment. Affinity is keyed by canonical thread ID and one canonical directory; Git origin is environment metadata, not Project identity. App Server `turn/start.cwd`, runtime command or shell `pwd`, explicit local inputs, sandbox, approvals, and writable roots do not rewrite or expand Project affinity. Failure leaves the thread projectless and usable, without a private pending/receipt state. The ordinary App does not own a managed Worktree/Handoff lifecycle.
- Workspace/cwd readiness is fail-open for the Codex-first shell: a missing or unavailable directory selector must leave projectless new task, composer input, explicit send-scoped local inputs, and ordinary Codex conversation available. Agent Package Workspace or managed-target validation applies only when the selected owner-projected action lists that context in `required_payload_fields`; the shell must not infer the requirement from a manifest. Readiness failure for one Agent Package must not disable ordinary Codex.

- The App ordinary path is a Codex CLI fixed-executor experience with configurable professional-agent shortcuts. Canonical first-party packages come from the Framework built-in Release Set, while starter shortcuts are App product metadata; neither is the upper bound of what OPL App can manage. It must not expose Aion CLI, Claude Code, or generic backend/provider switching as normal user choices; App-owned model/reasoning and user-language permission/access controls remain visible at the composer decision point.
- The default OPL Agent Registry is a configurable external GitHub/URL discovery directory only and may be empty. It must not claim any canonical first-party package id, first-party source, or `first_party` trust tier; Framework rejects such input with `agent_package_registry_first_party_identity_collision`. Settings Agents uses `app_state.agent_packages.directory.entries` as its only manageable collection and renders every Framework-projected built-in or external entry, installed or not. Directory entries own lifecycle/readiness and exact actions; status-index, runtime-source, module, Home shortcut, and static-profile data may enrich diagnostics or labels but cannot create rows or actions. Direct manifest installation stays in the Agents page's advanced install entry and requires an explicit user-selected `trust_tier`; registry-selected installation keeps its Framework-projected payload. OPL Framework owns its built-in Release Set, external-registry validation, package locks, canonical dependency/activation/guard/exposure diagnostics, action receipt and `rollback_ref` projection, manifest-declared physical Codex materialization, and lifecycle execution. The shell displays those refs and `materialized_required_skill_ids/paths` without inventing payloads or readiness. Agent Package `rollback_ref` remains a recovery reference, not an App- or Framework-owned rollback verb; installed Codex reload and live user-path evidence remain separate release/runtime evidence.
- The App home professional-agent shortcuts are not backend selectors and not strong session contracts. They launch Codex with the selected package's declared plugin/skill surface, and each created conversation must carry an App-owned invocation receipt that records launch facts only. The App must not use shortcut/profile metadata to decide domain workflow, prompt internals, stage behavior, artifact schema, readiness verdict, quality/export authority, or owner receipts.
- Ordinary Settings navigation 由 App 拥有。Settings must expose exactly ten ordinary product pages: Overview, Account & Gateway, Models, Workspace & Personalization, Agents, Capabilities, Resources & Connections, Maintenance, Data & Storage, and Preferences. About is the only independent secondary page. Advanced redirects to Maintenance diagnostics; Update, Theme, Local Services, and Personalization are compatibility deep links to their owner anchors. Gateway alone owns account, usage, credentials, refresh, repair, and disconnect; Models owns source and preferences; Resources excludes the built-in Gateway and its count; Workspace & Personalization owns the workspace path, App log directory, user AGENTS.md, and OPL App context; Storage references the log path read-only and owns usage/cleanup; Preferences owns App behavior/display; Maintenance diagnostics owns Framework and raw paths. Desktop log changes use the dedicated `application.setLogDirectory` action: persist `hostLogDir`, switch the live log writer, and roll the persisted value back with an explicit error if the switch fails. Shell returns only `hostLogDir`; `cacheDir` and `workDir` stay unchanged. WebUI `/data/logs` follows the existing `OnePersonLab/data -> /data` mount and Settings never rewires that volume. Storage keeps one `/settings/storage` product route across carriers: Desktop alone consumes Electron local lifecycle; WebUI never invokes that bridge, renders only valid owner projections, omits missing sections, preserves unknown bytes as unavailable, and never infers a destructive action from `host_action_required`. `contracts/app-settings-control-plane.json` is the machine-readable registry and behavior boundary over `settings_ia.v1`: carrier route ids remain `general` / `gateway` / `access` / `workspace` / `agents` / `capabilities` / `resources` / `environment` / `storage` / `appearance`; `SettingsHost` and `SettingsShellAdapterSlot` are implementation adapters, not product authority. The first interactive window renders a persisted narrow snapshot or loading shell, never waits for the complete fast projection or drilldowns, stays within the 1,500 ms cold/warm and 262,144-byte startup budgets, shares one background refresh, and lazy-loads Agents, Capabilities, Storage, and About details. Visual and timing evidence must cover all ten ordinary routes plus About and redirects; contract/tests alone do not prove installed timing or release readiness. Legacy overview/runtime/system/model/agent/assistants/skills-hub/tools/display/webui/pet routes 必须 redirect 到 App-owned pages，不能成为 normal user paths。
- `contracts/app-settings-control-plane.json#product_system_checklist` is the Settings Control Center completion-audit source. Each item requires fresh evidence for the slice being claimed. Installed App currentness, notarization, running version, and release readiness remain explicit release-owner-gated items and must not be inferred from Settings contracts, shell tests, screenshot QA, pushed commits, or active-shell validation.
- Settings visual QA is active-shell behavior evidence only. Screenshot or E2E visual coverage for Settings routes can close UI structure and overlap/framing risks, but it must not be used as release readiness, packaged App readiness, runtime currentness, owner acceptance, or production readiness evidence.

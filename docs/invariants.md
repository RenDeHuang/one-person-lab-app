# One Person Lab App Invariants

Owner: `one-person-lab-app`
Purpose: `app_invariants`
State: `active_truth`
Machine boundary: Human-readable invariants. Machine-readable truth lives in `contracts/`, source, release artifacts, updater metadata, and test results.

- The App repo owns desktop product packaging, release metadata, first-run product policy, App-level contracts, screenshots, user guides, and App validation wrappers.
- Temporary visual, Playwright, and Codex screenshots are local run artifacts, not repo truth. Keep them out of git unless they are promoted into `docs/site/latest`, a release evidence bundle, or an explicit manifest-backed evidence surface.
- The App repo is a purpose-first Codex wrapper product authority. It owns how users enter research, grant, presentation, and book work; it does not own the runtime, domain, memory, artifact, or family production truth behind those entries.
- The App repo owns One Person Lab App GUI product truth. The active shell may implement renderer/process/package/test/release-hook details and absorb upstream AionUI changes, but App page behavior, model-selection policy, onboarding policy, screenshots, and release/user docs stay App-owned.
- Conversation/session backed by the canonical Codex App Server thread ID is the primary user-work unit. Project affinity is `unbound | bound` and has zero-or-one cardinality: a new session may start projectless or bound. Only `custom_workspace=false` or no canonical recorded cwd may enter user-triggered one-time adoption; it writes `thread/settings/update.cwd`, requires exact `thread/read`, and commits local projection only after the returned cwd matches. Existing recorded cwd blocks `bound(A) -> bound(B)` reassignment. Affinity is keyed by canonical thread ID and one canonical directory; Git origin is environment metadata, not Project identity. App Server `turn/start.cwd`, runtime command or shell `pwd`, explicit local inputs, sandbox, approvals, and writable roots do not rewrite or expand Project affinity. Failure leaves the thread projectless and usable, without a private pending/receipt state. The ordinary App does not own a managed Worktree/Handoff lifecycle.
- Workspace/cwd readiness is fail-open for the Codex-first shell: a missing or unavailable directory selector must leave projectless new task, composer input, explicit send-scoped local inputs, and ordinary Codex conversation available. Agent Package Workspace or managed-target validation applies only when the selected owner-projected action lists that context in `required_payload_fields`; the shell must not infer the requirement from a manifest. Readiness failure for one Agent Package must not disable ordinary Codex.

- The App ordinary path is a Codex CLI fixed-executor experience with configurable professional-agent shortcuts. First-party packages come from the Framework directory and compatible source resolver, while starter shortcuts are App product metadata; neither is the upper bound of what OPL App can manage. It must not expose Aion CLI, Claude Code, or generic backend/provider switching as normal user choices; App-owned model/reasoning and user-language permission/access controls remain visible at the composer decision point.
- The default OPL Agent Registry is a configurable external GitHub/URL discovery directory only and may be empty. It must not claim any canonical first-party package id, first-party source, or `first_party` trust tier; Framework rejects such input with `agent_package_registry_first_party_identity_collision`. Settings Agents uses `app_state.agent_packages.directory.entries` as its only manageable collection and renders every Framework-projected built-in or external entry, installed or not. Directory entries own lifecycle/readiness and exact actions; status-index, runtime-source, module, Home shortcut, and static-profile data may enrich diagnostics or labels but cannot create rows or actions. Direct manifest installation stays in the Agents page's advanced install entry and requires an explicit user-selected `trust_tier`; registry-selected installation keeps its Framework-projected payload. OPL Framework owns its built-in directory/index, compatible source resolution, external-registry validation, installed package locks, canonical dependency/activation/guard/exposure diagnostics, action receipt and `rollback_ref` projection, manifest-declared physical Codex materialization, and lifecycle execution. The shell displays those refs and `materialized_required_skill_ids/paths` without inventing payloads or readiness. Agent Package `rollback_ref` remains a recovery reference, not an App- or Framework-owned rollback verb; installed Codex reload and live user-path evidence remain separate release/runtime evidence.
- The App home professional-agent shortcuts are not backend selectors and not strong session contracts. They launch Codex with the selected package's declared plugin/skill surface, and each created conversation must carry an App-owned invocation receipt that records launch facts only. The App must not use shortcut/profile metadata to decide domain workflow, prompt internals, stage behavior, artifact schema, readiness verdict, quality/export authority, or owner receipts.
- Ordinary Settings navigation 由 App 拥有。`settings_ia.v2` 必须把十个稳定 carrier routes 组织为七个一级组：Overview；Account & Models；Connections & Deployment；Workspace；Agents & Capabilities；Runtime & Maintenance；Preferences。About 是底部唯一辅助页。Resources & Connections 只归 Connections & Deployment；Instructions & Context 只归 Agents & Capabilities，并仅复用 Workspace personalization carrier；Workspace 只拥有 Working Directory 与 Data & Storage。Runtime & Maintenance 必须把 Service Status、Updates & Repair、Logs & Diagnostics 作为三个互斥二级目的地；Overview 只常驻一个 Background tasks 汇总，Temporal server/worker/scheduler 明细只在 Service Status。Desktop 日志目录由 Logs & Diagnostics 通过 `application.setLogDirectory` 管理并验证 `hostLogDir`；standalone WebUI 只读显示 owner/systemInfo 投影的实际日志目录，Docker WebUI 只读显示 `/data/logs`。Desktop workspace root 使用 Framework owner action；standalone WebUI 只读显示 owner 投影的实际逻辑 root，Docker WebUI 才由 `OPL_WORKSPACE_ROOT=/projects` 固定显示 `/projects`；任何 WebUI 都禁止执行 `workspace_root_set`。Docker WebUI 恰有两个必需宿主 bind：`/projects` 与 `/data`；Settings 永不修改宿主 source 或 bind，`/recovery` 只是可选 deployment-managed recovery staging。Storage 的部署位置摘要只在确认 Docker deployment identity 后显示。Storage 只读引用日志路径并持有 usage/cleanup；缺少完整 carrier-host ABI 时 WebUI cleanup 保持 status-only fail-open。Advanced、Update、Theme、Local Services、Personalization 仅作 owner destination 的兼容 deep link。`SettingsHost` 与 `SettingsShellAdapterSlot` 只是实现 adapter。首窗使用持久化窄快照或 loading shell，不等待完整 fast projection/drilldown，遵守 1,500 ms cold/warm 与 262,144-byte 预算。视觉与时序证据必须覆盖七组、全部二级目的地、十个 carrier routes、About 和 redirects；合同或测试不能单独证明安装与发布终态。

# One Person Lab App Decisions

Owner: `one-person-lab-app`
Purpose: `app_decisions`
State: `active_truth_with_history_notes`
Machine boundary: Human-readable decision record. Machine-readable truth lives in `contracts/`, source, release artifacts, updater metadata, test outputs, active shell validation, and OPL Framework CLI/read-model output consumed by the App.

## Current Decisions

| Decision | Current reading | Machine boundary |
| --- | --- | --- |
| App repo owns GUI product truth | App-level page behavior, model-selection policy, onboarding policy, screenshots, release/user docs, and release gates are governed from this repo. | `contracts/app-gui-product-contract.json`, `contracts/app-product-profile.json`, `contracts/app-page-state-matrix.json`, `contracts/app-first-run-test-matrix.json`, release scripts, and App tests. |
| Ordinary App executor is fixed to Codex CLI | The App home and ordinary conversation paths are a Codex App equivalent wrapper with built-in MAS/MAG/RCA entries. Aion CLI, Claude Code, generic backend switching, model override lists, and permission-mode controls are not normal user choices. | `contracts/app-gui-product-contract.json#executor_policy`, `contracts/app-product-profile.json#gui.home`, `contracts/app-page-state-matrix.json#guid_home`, active-shell validation, and shell GUI tests. |
| Home assistants carry scoped skill profiles | MAS/MAG/RCA are purpose entries over the fixed Codex executor. Each entry requires its matching Codex skill by default and exposes only relevant optional companion skills from the App packaged skill set. | `contracts/app-gui-product-contract.json#assistant_skill_profiles`, `contracts/app-product-profile.json#gui.assistant_skill_profiles`, `contracts/app-page-state-matrix.json#guid_home`, active-shell validation, and shell GUI tests. |
| Built-in assistant selection must be observable as a route receipt | Selecting MAS/MAG/RCA creates a Codex CLI conversation and persists `route_kind`, `executor`, `assistant_id`, `assistant_short_name`, and `source`; the receipt proves the route without exposing a backend selector. | `contracts/app-gui-product-contract.json#builtin_assistant_route_receipt_policy`, `contracts/app-product-profile.json#gui.builtin_assistant_route_receipt_policy`, `contracts/app-page-state-matrix.json#guid_home`, active-shell validation, and shell unit tests. |
| Ordinary Settings navigation is App-owned | Settings exposes Overview, Runtime, Capabilities, Access, Appearance, System, and About as normal tabs. Legacy upstream routes for model, agent, assistants, skills-hub, tools, display, webui, and pet redirect to App-owned pages; `/guid` opens Access rather than a WebUI-branded shortcut. | `contracts/app-gui-product-contract.json#settings_navigation`, `contracts/app-product-profile.json#settings`, active-shell validation, and shell Settings/Guid tests. |
| Skill is the public ABI; plugin is the App distribution shell | MAS/MAG/RCA remain domain skills backed by one action/stage metadata source. Codex App can expose them through plugin-packaged skills, while CLI/direct Codex paths use the same skill semantics. App install policy must not turn plugin-packaged domain skills into duplicate companion skill mirrors. | `contracts/app-install-exposure-policy.json`, `contracts/app-product-profile.json#companion_payloads`, OPL Framework `opl skill sync`, and active-shell validation. |
| App packaged skills use one whitelist | `default_packaged_codex_skill_ids` is the only App product default for skills that are both packaged and default visible. Candidate source is intentionally ignored: AionUI builtin, Skills Manager, Codex local skill, and plugin-packaged skill are all sources to copy from, not separate product policies. `packaged_not_default_visible_codex_skill_ids` is reserved for explicit-only packaged skills such as OMA. | `contracts/app-product-profile.json#companion_payloads`, Full first-install package scripts, full package manifest, and active-shell validation. |
| Active shell stays an external implementation carrier | `shells/aionui/` is the current active shell checkout from `gaofeng21cn/opl-aion-shell`; shell history and implementation truth stay in the shell repo. | `contracts/app-shell-adapter.json` and active-shell validation decide whether a shell satisfies the App contract. |
| Runtime page is project progress first | The App consumes `opl app state`, `opl app action`, and on-demand Framework drilldown output. Its daily Runtime page first shows project progress from `app_state.operator.workbench.task_drilldowns`: project title, domain, current state/stage, projected next step, blockers, and user-facing progress delta labels. Operator summary, safe actions, evidence refs, and full detail stay as secondary diagnostics. The App does not own runtime truth, provider implementation, domain truth, progress truth, memory body, artifact body, owner receipt authority, or domain verdicts. | `contracts/app-runtime-bridge.json`, `contracts/app-page-state-matrix.json`, `contracts/fixtures/opl-app-state-fast.fixture.json`, and OPL Framework CLI/read-model output. |
| WebUI uses the same chat-first authority as desktop | A WebUI-capable candidate must reuse the Electron React/CopilotKit renderer and expose the same App-owned `window.oplCandidate` bridge shape through browser transport. WebUI is not a second product profile, runtime source, provider selector, memory store, artifact store, release channel, or full workbench first screen; ordinary WebUI home opens with rail and inspector collapsed. | `contracts/app-shell-candidates.json#candidates[agui-codex].webui_transport`, `scripts/validate-shell-candidates.ts`, and candidate WebUI smoke. |
| External UI projects can inform information organization without becoming authority | PilotDeck is a reference for optional workspace/session rail, chat-first main pane, grouped files, memory, routing, and always-on context. Its AGPL source and runtime are excluded unless a separate license and candidate-adoption decision is made, and it is not a first-screen workbench template. | `contracts/app-shell-candidates.json#design_references` and `docs/app-gui-feature-inventory.md#PilotDeck-Informed Information Organization`. |
| Standard updater and Full first-install assets stay separate | Standard updater metadata must never select `Full` assets. Full first-install evidence remains a separate release gate and must not be promoted from missing artifacts. | `contracts/app-release-channel.json`, release evidence manifests, remote release verification, and first-run VM evidence. |
| App docs use a lighter lifecycle taxonomy | The App keeps only App-owned long-lived docs directories. Framework/domain-agent taxonomy directories are added only when App material has a clear owner, purpose, state, and machine boundary. | `docs/docs_portfolio_consolidation.md`, `docs/README.md`, and repo docs inventory. |

## Superseded Readings

| Superseded reading | Current reading |
| --- | --- |
| AionUI implementation defaults can define One Person Lab App product truth. | AionUI is implementation material; App product truth is contract-backed from this repo. |
| Upstream AionUI multi-Agent controls are power-user App features. | They are implementation material or diagnostics; the App ordinary path is fixed Codex CLI plus built-in MAS/MAG/RCA purpose entries. |
| Upstream AionUI model/agent/tools/webui Settings tabs are ordinary App settings. | They are legacy or diagnostics routes that redirect to App-owned Runtime, Capabilities, Access, or Appearance pages. |
| App release or UI rendering can prove MAS/MAG/RCA/OMA readiness. | App release artifacts, UI rendering, and provider/read-model availability are App or Framework evidence only; domain readiness remains domain-owned. |
| Full first-install assets can be served through the standard updater channel. | Full assets are separate first-install downloads and remain outside updater metadata. |
| AionUI builtin skills should be separately classified as App defaults. | AionUI builtin skills are candidate capabilities only. A skill enters the App package only through the App-level packaged whitelist or the explicit-only packaged list. |
| A polished external UI can be copied wholesale into OPL App or define the first screen. | External UIs such as PilotDeck may inform OPL-owned information organization, but source/runtime adoption must pass license, authority, adapter, package, and release-isolation gates first. The ordinary App surface remains chat-first with contextual inspector surfaces. |
| A WebUI candidate can define separate App state or runtime truth because it runs in a browser. | WebUI is only another delivery surface for the same chat-first App UI and must use the same renderer, bridge shape, product profile, Codex backend, and OPL state/action authority boundary. |

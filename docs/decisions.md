# One Person Lab App Decisions

Owner: `one-person-lab-app`
Purpose: `app_decisions`
State: `active_truth_with_history_notes`
Machine boundary: Human-readable decision record. Machine-readable truth lives in `contracts/`, source, release artifacts, updater metadata, test outputs, active shell validation, and OPL Framework CLI/read-model output consumed by the App.

## Current Decisions

| Decision | Current reading | Machine boundary |
| --- | --- | --- |
| App product truth is purpose-first | The App is a Codex wrapper for ordinary users to enter research, grant, and presentation work. It owns the App/product boundary and user path, while runtime, domain, memory, artifact, owner receipt, and production-readiness truth stay with OPL Framework and domain owners. | `contracts/app-product-profile.json#boundary`, `contracts/app-gui-product-contract.json#product_authority`, `docs/project.md`, and `docs/architecture.md`. |
| App repo owns GUI product truth | App-level page behavior, model-selection policy, onboarding policy, screenshots, release/user docs, and release gates are governed from this repo. | `contracts/app-gui-product-contract.json`, `contracts/app-product-profile.json`, `contracts/app-page-state-matrix.json`, `contracts/app-first-run-test-matrix.json`, release scripts, and App tests. |
| GUI 定义栈由 App 拥有 | 理想交互细则、Codex-to-OPL 产品增量、GUI 能力清单和机器 contracts 构成一组定义栈。修改 shell 行为前，GUI implementation work 应按这个顺序阅读。 | `docs/app-ideal-gui-interaction-spec.md`, `docs/codex-to-opl-app-delta.md`, `docs/app-gui-feature-inventory.md`, and `contracts/`. |

| Model selector is visible and defaults strongest | Home and ordinary Codex conversations show the App default model plus reasoning effort as `GPT-5.5（超高）`, and expose an App-owned model selector. | Home assistants carry scoped skill profiles | MAS/MAG/RCA are purpose entries over the fixed Codex executor. Each entry requires its matching Codex skill by default and exposes only relevant optional companion skills from the App packaged skill set. | `contracts/app-gui-product-contract.json#assistant_skill_profiles`, `contracts/app-product-profile.json#gui.assistant_skill_profiles`, `contracts/app-page-state-matrix.json#guid_home`, active-shell validation, and shell GUI tests. |
| Ordinary skill/MCP selection is OPL allowlist only | The ordinary Home composer and ordinary conversation loaded-capability surfaces use `gui.ordinary_capability_selector_policy`: visible skills are derived from MAS/MAG/RCA assistant profiles, and visible MCP servers default to an empty App allowlist. AionUI implementation skills such as `aionui-skills`, `aionui-webui-setup`, `skill-creator`, `cron`, and unlisted MCP servers are excluded from ordinary selection, loaded-capability display, and new conversation create payloads. | `contracts/app-product-profile.json#gui.ordinary_capability_selector_policy`, `contracts/app-gui-product-contract.json#ordinary_capability_selector_policy`, `contracts/app-page-state-matrix.json#guid_home`, active-shell validation, `GuidPage`, `useGuidSend`, `FileAttachButton`, `ConversationSkillsIndicator`, and shell whitelist tests. |
| Built-in assistant selection must be observable as a route receipt | Selecting MAS/MAG/RCA creates a Codex CLI conversation and persists `route_kind`, `executor`, `assistant_id`, `assistant_short_name`, and `source`; the receipt proves the route without exposing a backend selector. | `contracts/app-gui-product-contract.json#builtin_assistant_route_receipt_policy`, `contracts/app-product-profile.json#gui.builtin_assistant_route_receipt_policy`, `contracts/app-page-state-matrix.json#guid_home`, active-shell validation, and shell unit tests. |
| Ordinary Settings navigation 由 App 拥有 | Settings 正常 tabs 是 General、Access、Agents & Capabilities、Local Environment、Appearance、Advanced、About & Updates。Overview、runtime、system、model、agent、assistants、skills-hub、tools、display、webui、pet 等 legacy upstream routes redirect 到 App-owned pages；`/guid` 打开 Access，而不是 WebUI-branded shortcut。 | `contracts/app-gui-product-contract.json#settings_navigation`, `contracts/app-product-profile.json#settings`, active-shell validation, and shell Settings/Guid tests. |
| Home minimal command surface and Settings IA require matrix parity | Home is composer-first and does not show runtime activity, continue-work, per-assistant running badges, or footer quick icons. Runtime/secondary context refs plus General/Access/Capabilities/Local Environment/Advanced sections must be declared in both the GUI product contract and page-state matrix. | `contracts/app-gui-product-contract.json#pages`, `contracts/app-page-state-matrix.json#pages`, `scripts/validate-active-shell.ts`, and focused release-boundary GUI tests. |
| Skill is the public ABI; plugin is the App distribution shell | MAS/MAG/RCA remain domain skills backed by one action/stage metadata source. Codex App can expose them through plugin-packaged skills, while CLI/direct Codex paths use the same skill semantics. App install policy must not turn plugin-packaged domain skills into duplicate companion skill mirrors. | `contracts/app-install-exposure-policy.json`, `contracts/app-product-profile.json#companion_payloads`, OPL Framework `opl skill sync`, and active-shell validation. |
| Codex configuration syncs App-visible OPL family plugins | Fresh Full installs must not require a second manual Codex plugin setup after the API key is configured. `opl system configure-codex --api-key-stdin` consumes the Full runtime module paths, syncs MAS/MAG/RCA plugin-packaged skills, generates the OMA local plugin surface, and writes the Codex plugin registry in the same setup step. | OPL Framework `system configure-codex`, `syncFamilySkillPacks`, App Full runtime wrappers, and release-boundary wrapper validation. |
| First conversation waits for ACP warmup, not Full readiness | First-run Core readiness still requires only workspace root, Codex CLI, and Codex config before `/guid`. The first `/guid` message must wait for the conversation record and ACP warmup before `sendMessage`, so slow first-run dependency unpacking does not become a fixed 30-second ACP handshake failure. Domain modules, Codex plugin sync, and Temporal provider readiness stay visible background maintenance. | `contracts/app-install-exposure-policy.json#setup_flow_contract.first_conversation_readiness`, `contracts/app-product-profile.json#first_run.first_conversation`, active-shell `useAcpInitialMessage`, and shell unit tests. |
| Temporal defaults are App-configured and OPL-owned | The App may configure default Temporal environment for the packaged OPL runtime, but it does not own provider implementation or runtime truth. OPL Framework owns service start, worker status/start, residency proof, lifecycle diagnostics, and repair receipts. | `contracts/app-install-exposure-policy.json#temporal_auto_configuration`, `contracts/app-release-channel.json#full_first_install.required_payloads.temporal_runtime_provider`, `scripts/full-first-install-runtime-wrappers.ts`, `scripts/verify-full-runtime-native-trust.ts`, and OPL Framework family-runtime commands. |
| Agent-pack channel failures fail closed with packaged fallbacks | A missing or unavailable GitHub Packages/GHCR agent-pack tag is a package-channel failure, not a reason to hand-install a divergent OMA surface. The source order is bundled Full runtime modules, App/CLI-managed stable package channel, then explicit Developer Profile checkout override. Failures surface as actionable background-maintenance errors while preserving one Codex-visible plugin/skill semantic path. | `contracts/app-install-exposure-policy.json#agent_installation_contract.managed_agent_pack_distribution`, `npm run validate:agent-installation`, Full runtime module path wrappers, and OPL Framework `opl module reconcile` / `opl skill sync`. |

AionUI helper skills such as `aionui-skills` do not surface as OPL App capabilities. | `contracts/app-gui-product-contract.json#pages.settings_capabilities`, `contracts/app-page-state-matrix.json#capabilities`, `contracts/app-product-profile.json#companion_payloads.default_packaged_codex_skill_ids`, `SkillsHubSettings`, active-shell validation, and shell tests. |

## Superseded Readings

| Superseded reading | Current reading |
| --- | --- |
| AionUI implementation defaults can define One Person Lab App product truth. | AionUI is implementation material; App product truth is contract-backed from this repo. |
| Upstream AionUI multi-Agent controls are power-user App features. | They are implementation material or diagnostics; the App ordinary path is fixed Codex CLI plus built-in MAS/MAG/RCA purpose entries. |
| Upstream AionUI overview/runtime/system/model/agent/tools/webui Settings tabs 是普通 App settings。 | 它们是 legacy 或 diagnostics routes，redirect 到 App-owned General、Local Environment、Agents & Capabilities、Access、Appearance、Advanced 或 About & Updates pages。 |
| App release or UI rendering can prove MAS/MAG/RCA/OMA readiness. | App release artifacts, UI rendering, and provider/read-model availability are App or Framework evidence only; domain readiness remains domain-owned. |
| Full first-install assets can be served through the standard updater channel. | Full assets are separate first-install downloads or the explicit `one-person-lab-full` Homebrew cask and remain outside standard updater metadata. |
| A Homebrew receipt can prove the App is activated or release-ready. | Homebrew proves only that the tap resolved and installed or upgraded indexed files. User-state activation and readiness remain `opl system initialize --json` plus App release gates for the matching cohort. |
| A Nightly Homebrew tap can share the stable/latest formula target. | Nightly distribution remains an explicit prerelease/opt-in lane and points only at Nightly standard assets. It does not mark GitHub latest, select Full assets, or replace stable tap promotion. |
| AionUI builtin skills should be separately classified as App defaults. | AionUI builtin skills are candidate capabilities only. A skill enters the App package only through the App-level packaged whitelist or the explicit-only packaged list. |
| A polished external UI can be copied wholesale into OPL App or define the first screen. | External UIs such as PilotDeck may inform OPL-owned information organization, but source/runtime adoption must pass license, authority, adapter, package, and release-isolation gates first. The ordinary App surface remains chat-first with contextual inspector surfaces. |
| A WebUI candidate can define separate App state or runtime truth because it runs in a browser. | WebUI is only another delivery surface for the same chat-first App UI and must use the same renderer, bridge shape, product profile, Codex backend, and OPL state/action authority boundary. |
| A GUI feature inventory alone is enough to guide shell design. | Shell design must use the App-owned interaction spec and Codex-to-OPL delta first, then the feature inventory and machine contracts for implementation and validation. |
